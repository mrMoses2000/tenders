# Owner-authorized four-hour procurement flow: next-patch strategy

Status: implementation proposal only. This document changes no runtime code, database schema, or provider settings. Migration numbering assumes the in-flight account-agent migration is `043`; the next schema change would be `044`.

## Target behavior and consent boundary

An owner explicitly enrolls an owner/project in **research autostart** once. After that, a new Telegram PDF/DOCX for that enrolled scope may be extracted, normalized, given a deterministic research plan, and started without a per-case button click. Enrollment is off by default, belongs to the authenticated case owner, and applies only to new cases bound to that profile. A case without a matching active profile keeps today's approval-card flow.

Research consent does not authorize WhatsApp messages. Supplier-contact automation continues to require the existing case-scoped `case_auto_send_policies` episode (`migrations/034_case_auto_send_policy.sql`, `src/procurement_bot/auto_send_policy.py:set_case_auto_send_policy` and `authorize_and_enqueue_auto_whatsapp`). If that separate consent or outbound transport is absent, research may collect public supplier evidence, but it must not send WhatsApp messages. A research profile must never create or enable a WhatsApp policy.

“Four hours” is a report/SLA checkpoint from the first approved research start. At the checkpoint, publish a clearly dated shortlist with confirmed quotes, unconfirmed listings, unresolved item flags, provider failures, and pending supplier replies. Keep eligible work running or waiting under the existing retry/runtime policy. Do not label the market exhausted, close the case, or stop work merely because four hours elapsed. The case delivery address remains separate from the ordered sourcing cities.

## Small additive persistence design

Use a single additive migration `044_owner_research_autonomy.sql`; keep all existing `action_approvals`, research run/query/checkpoint, pipeline runtime, and WhatsApp policy tables. Do not create a parallel job engine.

1. `owner_research_automation_profiles`: immutable consent/policy episode keyed by owner and optional project (`customers.id`, null for an owner-wide profile). Store profile version, `research_autostart`, ordered source-city tiers, sourcing mode, four-hour report SLA, per-item ambiguity behavior, consent reference/text, policy JSON/hash, `authorized_at`, and `revoked_at/by`. Permit one active episode per owner/project. Consent and policy facts do not change in place: changing configuration revokes the prior episode and inserts a new version. Default is no active row (off). Do not put WhatsApp enablement in this table.
2. `case_research_policy_snapshots`: one immutable snapshot per case/intake version, FK-linked to the exact active profile episode and owner/project at capture. Store the resolved policy JSON and SHA-256, profile version, intake version, case owner/project identity, and capture time. Enforce no update/delete of snapshot facts. Revoking the profile blocks future autostarts and causes the pipeline to pause at the next guarded tick; it does not rewrite historic consent evidence. Existing cases with no snapshot retain their current behavior.
3. Add an immutable owner-evidence disposition projection (or equivalent validated snapshot payload) for per-item source exclusions/reduced quantities, linked to the original source artifact hash and exact item IDs, separate from accounting purchase tables. Add only the runtime fields needed to resume the feature: snapshot FK, active city-tier ordinal, and report-deadline timestamp. Keep the immutable one-city research plan in `research_runs.search_scope`; advance by creating the next native run only after the current tier's eligible item branches have reached their defined completion/timeout boundary. The transition event is idempotent and identifies the old run, new run, policy snapshot, tier ordinal, and unsatisfied item IDs. If implementation cannot prove these updates atomic with `workflow_events` and job enqueue, split this runtime extension into a later patch rather than store an unresumable in-memory cursor.

Owner/project enrollment must be explicit and owner-authenticated. The narrow UI/API change should display the actual policy before enabling it and persist a consent reference/text. An owner-wide profile can serve cases without a customer link; a project-specific profile can serve only cases whose `customer_id` is that project. Never fall back from an unmatched project to another project's profile. Any profile-creation/revocation route must use the Mini App's authenticated `request["owner_id"]` and verify the customer belongs to that owner.

## City sequencing, deadlines, ambiguity, and purchases

The profile stores an ordered list `Тараз → Шымкент → Алматы`; it is not a set of concurrent geographies. A research run contains one active city only. Use native source/provider branches within that city. Advance to the next city when the current tier's discovery branches complete for unsatisfied items, or when a configured tier wait expires. A pending supplier reply does not hold discovery in the current city open. A provider outage is recorded as unavailable coverage, never as evidence that the city had no suppliers; it may be bypassed after its bounded wait so other cities/providers can proceed, while the report preserves the uncovered-source failure. A satisfied item is excluded from later-tier plans; unsatisfied items continue. Exhausting all configured tiers means only “no further candidate found in the configured sources/cities as of timestamp,” and only for providers that actually completed. The four-hour report may precede tier completion.

Keep `ParsedProcurementRequest.city`/`search_scope` and `delivery_address` distinct. The policy's ordered cities are sourcing coverage; they never overwrite destination. Each query, candidate, contact attempt, and shortlist item should retain the city tier that produced it.

An item whose name, quantity, and unit are known but whose spec has an unresolved conflict remains an item-level ambiguity. It cannot block other clear lines from search. For an unresolved specification conflict, search both source-backed variants (or search by product name while retaining both requirements as an explicit conflict); do not choose one, call the item conforming, or silently contact a supplier on a false exact spec. No currency/price estimate is required to search. If a supplier quote lacks confirmed currency, preserve amount/currency as unknown and do not rank a money total.

Buying assumptions are scoped to this owner/project policy: the buyer may purchase as a natural person. Compare explicit final payable amounts, currency, unit/pack size, requested quantity, and delivery terms. VAT is not a conformity gate and must not be deducted, added, or assumed by default; retain only what the supplier explicitly quotes. RFQ templates should ask for the final price for an individual buyer, its currency and unit/pack size, stock/quantity, and delivery cost/terms, without requesting corporate paperwork. This is a case/project preference, not a global default for all customers.

There is a related currency trap in the ordinary intake path: `_parse_priced_table` previously parsed a numeric tender-price cell without validating currency, while `cases.py:_replace_item_projection` writes a non-null `tender_unit_price_private` with `currency='KZT'`. Reviewed imports that explicitly contain null tender prices remain unchanged; future autoparse must not treat an unstated document currency as KZT. Keep the price null unless the source explicitly establishes its currency, while still allowing product search and non-financial shortlist progress.

Do not re-source quantity already bought when there is exact, item-level evidence. Formal accounting linkage (`purchase_items` → `purchase_documents` → source artifact) is valid evidence, but it is not the only valid proof: the owner may explicitly say an item was bought and attach a photo/receipt whose content maps to that exact requested item and quantity even when the seller/receipt is unreadable. Record a separate immutable sourcing disposition with the owner assertion verbatim, source artifact ID and SHA-256, exact request-item ID, mapped quantity/unit, evidence/matching rationale, disposition (`skip` or `reduce_quantity`), and actor/time. This affects research quantities only; it does not create a `purchase_item`, price, vendor, financial row, or closed/completed status. Compute remaining research quantity from requested quantity less evidence-backed quantity, bounded at zero after exact compatible-unit validation.

For an owner-reviewed receipt or photo, exclude or reduce only the exact item mappings and quantities explicitly confirmed by the owner. Receipt line count, unreviewed candidate mappings and case totals do not prove that requested items were bought. Never auto-map those candidates. Expose “Куплено по фото/словам владельца” separately from “Закуплено, подтверждено” formal accounting in the Mini App, with a reviewable evidence link.

## Compatibility, failure behavior, and rollout

- The feature is opt-in; absence, malformed consent, stale profile version, owner/project mismatch, or revoked profile follows the current manual approval path or blocks the automatic start.
- Telegram updates, attachment hashes, extraction versions, intake versions, research plan hashes, approval payloads, city-tier transition events, and jobs each retain deterministic idempotency keys. A replay of the same document must resolve to the same source/case/approval/run identities; changed content creates a new intake version and requires a newly validated plan/authorization.
- A valid deterministic DOCX table can be normalized without AGY; arbitrary PDF/DOCX extraction still needs its configured provider. Do not add a global AGY auth gate to providers that do not use AGY. If extraction is unavailable, keep the file and retry/review state without starting an empty plan.
- Public research can run when WhatsApp outbound is disabled. No supplier reply means a listing is not a confirmed quote; show “ответа нет/ожидается” and keep the dialogue separate from a public listing.
- Roll out with a test profile/case first, then an explicit owner/project enrollment. Migration creates no active profiles and must not activate any old case. Do not turn on the historical Uran WhatsApp policy or copy it into the new case's research consent.

The project-local importer used for the current manual-source case is a separate explicit operator path: `operator_case_import.py:apply_operator_import` validates an exact reviewed request against the existing item projection and preserves item IDs, but then directly writes the parse version, requirements, ready statuses, and provenance event. It does not invoke `IntakeService.evaluate_missing_blockers`; `_prepare_research` later validates the normalized model and builds a plan directly. That means an unresolved specification conflict must be retained as a warning/requirement conflict in the imported payload and surfaced downstream; it must not be “fixed” by forcing the normal all-item clarification evaluator or by dropping unrelated rows. The current import CLI itself does not start research; the next integration must enqueue/use the native prepare/start path after the reviewed import, rather than inventing a fake Telegram source event. For automated start events, distinguish `authorization_mode=owner_research_profile` in persisted event data so the existing `actor_type='user'` approval projection is not misread as a fresh per-run click.

## Narrow intake currency hotfix (separate from owner-autonomy migration)

Before migration `044`, land one backward-compatible bug fix in the existing seven-column document parser. Before the separate currency hotfix it read a numeric price from a generic `Цена` header as `tender_unit_price_private`; `cases.py:_replace_item_projection` persists any such non-null amount as KZT. Only an explicit, unambiguous KZT marker in the source price-column header may keep the existing numeric private-price behavior. A generic `Цена`, explicit USD, or any other unrecognized/foreign-currency marker must leave `tender_unit_price_private=None`, append a warning to the already-existing `ParsedProcurementRequest.warnings`, and preserve all product names, quantities, units, specifications, source references, and searchable rows. Do not infer currency from Kazakhstan, supplier city, filenames, or numeric formatting. Do not add request fields or alter frozen request hashes. The original document/extraction artifact remains the evidence for the raw amount.

Acceptance for this narrow patch: (1) unqualified/generic price header parses all item facts but yields no private price plus a warning; (2) explicit KZT header preserves the existing price value; (3) explicit USD header does not reinterpret the value as KZT and warns; (4) a real native PostgreSQL `persist_intake_result` test proves the unknown-currency case inserts zero `request_item_financials` rows while preserving item rows and the searchable case state; (5) the exact current operator import remains unchanged because its reviewed request prices are already null. Test the parser and persistence path without production DSNs; this fix requires no migration and must not expand into owner-profile work.
