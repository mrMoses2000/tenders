## Why `source_evidence` can exist without an offer

`source_evidence` is a generic immutable provenance record. It can describe a captured URL, manual source or imported evidence. It is intentionally not itself a supplier, product variant, offer, priced observation or purchase, and the table has no `offer_id` foreign key. Evidence may therefore be valid while no offer exists.

The owner manual-quote API documented in the October 9 release accepts an existing `case_id` and `offer_id`; its transaction writes a manual `source_evidence` record, an `offer_observations` row and a versioned quote snapshot linked to that existing offer. It cannot create a supplier or an offer. If a manual branch wrote source evidence without an offer, the likely explanation is that capture/persistence ran before supplier identity and product-variant association. Repository code supports that architectural explanation, but the exact historical row/event and branch cannot be confirmed from local docs alone; use the live read-only audit to inspect IDs, idempotency keys, evidence payload shape, events and foreign-key links before attributing the cause.

Do not “repair” orphan evidence by guessing a supplier, product or request item. Preserve the evidence and link it only after a human can establish that identity and the source supports the claim.

## Canonical table paths

| Business fact | Existing canonical path | Reconciliation rule |
|---|---|---|
| Original Telegram PDF/DOCX | `messages` → `incoming_attachments` → `source_artifacts` (`original`) → `content_extractions` | Preserve original message/attachment/artifact identities and hashes. Record extraction engine/version and status. Classify whether it is a customer request, supplier quotation, invoice, receipt or another document before updating the case. Extraction output is evidence, not an approved case mutation by itself. |
| Existing request | `procurement_cases` → `request_items` → requirements/clarifications | Match to the existing UranEnergo case by owner, title/source and stable item IDs. Verify all 55 original item identities, names, quantities, units, requirements and customer/tender prices before any reconciliation. Do not recreate the request from a supplier quote or replace the 55-row baseline. |
| Supplier identity | `source_evidence` → `suppliers`, `supplier_aliases`, `supplier_contacts`, `supplier_locations` | Resolve business identity and contact provenance; merge only on strong evidence. A directory card or phone alone does not prove product suitability or current price. |
| Candidate product and price | `offers` (request item + supplier + product/model) → `offer_observations` (source evidence, observed facts, price/availability/terms) → current/versioned quote snapshot | Reuse an existing exact candidate when source and product match. Create a distinct offer when a different product variant is supported. Preserve unknown values as unknown; never overwrite tender revenue with supplier price. Manual quotes use `source_type='manual'` and must keep their operator-entered provenance. |
| Completed purchase | `purchase_documents` → `purchase_items` (with optional `offer_id`) and existing execution/accounting events | Record only an actual purchase, its source artifact or explicit user-reported provenance/note, matched line, quantity, unit cost and currency. A quote is not a purchase; a purchase document does not prove supplier delivery or customer acceptance. |
| Receipt or waybill awaiting details | `purchase_evidence_requests` bound to the owner's `incoming_attachments` and `source_artifacts` | Existing Telegram receipt path first attaches an expected document to its explicit request. Do not interpret an arbitrary next attachment as a purchase or mark the line closed without the established details/evidence workflow. |

Existing migrations already define these entities. This plan proposes **no schema writes and no migration**. If the read-only audit finds a missing canonical relation, pause at a concrete migration design and compatibility review; do not make ad hoc SQL changes in production.

## Four-hour unattended work sequence

1. **Read-only preflight.** On the server, confirm intended application checkout/commit, service health, DB connection identity, current case ID/owner, live run and lease state, frozen 55-item baseline and migration checksums. Keep secrets and raw file contents out of output. Verify the WAHA account's configured self-test number against its live account identity before accepting inbound dialogue; never print the number.
2. **Verify the actual Telegram document path.** Use an owner-provided PDF/DOCX through the existing Telegram bot. Confirm message → attachment → original artifact → extraction record → structured, validated rows. If it is a supplier quote, link it to the right case and one or more request lines only after checking source, item, quantity, unit, price currency/unit, validity date, delivery location and seller identity. If it is a new request, preserve it as a separate intake until the owner confirms it is UranEnergo. Do not fabricate rows from unreadable pages.
3. **Reconcile existing evidence first.** Inspect all 55 item identities, saved offers and current observations, orphan `source_evidence`, history and open research states. Associate a source with an offer only from traceable supplier/product facts. Keep the historical worklist as leads, not current quotations. Avoid duplicate supplier identities and offers using existing idempotency and deduplication rules.
4. **Run bounded supplier discovery in the requested logistics order:** Taraz first, then Shymkent, then Almaty. Use current item requirements and the existing browser/AGY providers to gather candidate sources. Distinguish company/contact discovery from evidence that a product exists, matches the requirement or has a current price. Persist each result in the existing research/evidence/supplier/offer tables and keep the Mini App shortlist tied to those records.
5. **Keep dialogue and shortlist truthful.** Where the existing WAHA account and guards are healthy, use the app's existing supplier conversation targets and exact-message approval/outbox flow. Confirm shared-chat identity and prior history before a send. Never replay a message whose prior acceptance/delivery is unknown. Store replies against their exact conversation/offer/item target; record explicit price, unit, availability, delivery terms and source time as observations. Ambiguous replies stay for owner review. If outbound gates block or no current consent is established, continue read-only discovery and present the shortlist without claiming supplier confirmation.
6. **Operate unattended for the four-hour window.** Let existing durable jobs/leases and schedulers resume work; inspect progress without repeatedly enqueueing or retrying the same item. Keep retries bounded and preserve quota, quiet-hour, opt-out, geolocation, exact-recipient, approval and unknown-send protections. Record per-line outcomes and reasons. Do not change service/session configuration, release a hold, create migrations or modify customer records during the unattended window.
7. **Final reconciliation.** Re-read the baseline and all affected row counts/hashes. Confirm which source files parsed, which 55 lines have supplier evidence, which have a quote from a supplier, which technical facts remain unverified, which leads are only contacts, and which price/availability facts are stale or unknown. Surface a concise shortlist in the existing Mini App/report with supplier, product, source, current quote time, unit basis, availability, delivery city and fit status. Do not mark a supplier selected or a purchase completed merely because it ranks first.

## Minimum evidence for the shortlist

- Case item ID and the original item description/specification remain traceable.
- Supplier legal/display identity and contact/location have evidence; duplicate and cross-item conversation history have been checked.
- Product/model/SKU and technical claims have a source and explicit verification status.
- Supplier quote date, amount, currency, price unit, pack quantity/MOQ, stock and delivery terms are stored as observations; missing fields stay unknown.
- A supplier's explicit answer is distinct from a public listing, directory lead or model-extracted guess.
- No customer tender price is disclosed to suppliers or treated as their quote.
