# База `Предложения`: полный справочник полей

Актуально на: 2026-07-13
Notion: [`Максим → Предложения`](https://app.notion.com/p/688d47b6a5b249cab9431df3fd7e34bf)
Data source: `collection://30f4933a-6bf6-4c2f-bf52-19304b4a8231`

## Главная идея

Одна строка `Предложения` — это одно конкретное предложение одного поставщика по одной позиции заявки, проверенное в определенную дату.

```text
Заявка №23
└── Поставщик: МЕГАСТРОЙ
    └── Товар: корзина P139, 9 л
        └── Наблюдение 2026-07-09: 800 ₸/шт., наличие не подтверждено
```

Если цена или существенные условия изменились, создается новое датированное наблюдение. Полезная история не стирается.

## Типы полей

| Метка | Кто управляет | Правило |
|---|---|---|
| Ручное | Агент или пользователь | Заполнять только из источника, ответа поставщика или факта пользователя. |
| Relation | Notion + агент | Связь с другой базой. Не заменять существующие связи без причины. |
| Rollup | Notion | Автоматически читает значение из связанной записи. Не редактировать. |
| Formula | Notion | Автоматический расчет. Не редактировать. |
| Legacy | Только совместимость | Не использовать для новой работы; скрыть из рабочих views. |

## 1. Идентификация предложения

| Поле | Тип | Кто заполняет | Назначение и пример |
|---|---|---|---|
| `Предложение` | Title | Агент | Короткое уникальное название: `№23 · МЕГАСТРОЙ · корзина P139 9 л`. |
| `Ключ наблюдения` | Text | Агент/скрипт | Устойчивый ключ `offer:v3:<sha256>`. Нужен для повторного запуска без дублей; вручную не редактировать. |
| `Заявка` | Relation → `Заявки` | Агент | Ровно одна исходная позиция тендера. Через нее приходят количество и тендерная цена. |
| `Поставщик` | Relation → `Поставщики` | Агент | Одна компания, продавец или торговая точка, если личность источника установлена. |
| `Выбрано в заявке` | Обратная relation | Notion | Показывает, что это предложение выбрано в `Заявки.Выбранное предложение`. Вручную не менять. |
| `Товар поставщика` | Text | Агент | Название продавца без переписывания исходного техспека: `Корзина Р139, 9 л, пластик, черный`. |
| `Модель / артикул` | Text | Агент | SKU, модель или заводской артикул: `P139`. |
| `Фасовка / размер` | Text | Агент | Размер, вес, объем или комплектность: `9 л`, `50 кг`, `10 шт. в упаковке`. |
| `Количество в ценовой единице` | Number | Агент | Сколько содержимого входит в одну единицу цены: например, `1000` скоб в упаковке. Только доказанное значение. |
| `Единица содержимого` | Select | Агент | Единица содержимого упаковки: `шт.`, `кг`, `м`, `пара`, `л`. |

Не смешивать:

- товар поставщика — что продается;
- модель — какая конкретно модификация;
- фасовка — сколько или какого размера находится в единице продажи.

## 2. Источник и доказательства

| Поле | Тип | Назначение |
|---|---|---|
| `Тип источника` | Select | Канал, из которого получено наблюдение. |
| `Источник` | URL | Прямая карточка товара, объявление или страница магазина. |
| `Источник фото` | URL | Стабильная прямая ссылка на изображение, не ссылка на страницу товара. Необязательно. |
| `Фото товара` | Files | Загруженный скриншот, фото поставщика или фактическое фото товара. |
| `Дата проверки` | Date | Когда источник или ответ проверяли последний раз. |
| `Уровень доказательств` | Select | Степень доверия к наблюдению. |
| `Доказательства` | Text | Кратко: что доказано, откуда цена, какие параметры совпали и какие риски остались. |
| `Что подтвердить` | Text | Конкретные недостающие сведения для звонка или сообщения. |
| `Сообщение поставщику` | Text | Готовый черновик WhatsApp. Агент не отправляет его автоматически. |

### `Тип источника`

| Значение | Когда использовать |
|---|---|
| `Сайт` | Официальный сайт, каталог или интернет-магазин. |
| `Kaspi` | Карточка товара или продавец Kaspi. |
| `OLX` | Объявление OLX. |
| `2ГИС` | Компания или физическая точка, найденная через 2GIS. |
| `Instagram` | Профиль, публикация или витрина продавца. |
| `Рынок / офлайн` | Базар, ряд, павильон, склад или физическая проверка. |
| `Прошлая закупка` | Фактическая цена из собственной истории. |
| `Телефон / WhatsApp` | Условия получены напрямую от поставщика. |

### `Уровень доказательств`

| Уровень | Что доказано | Что еще нельзя утверждать |
|---|---|---|
| `1 — Гипотеза` | Поставщик или рынок потенциально может иметь товар. | Цену, наличие и точный товар. |
| `2 — Публичный лид` | Существует публичная компания, страница или объявление. | Что карточка актуальна и товар соответствует ТЗ. |
| `3 — Карточка проверена` | Агент изучил карточку, цену и доступные параметры. | Реальный остаток, документы и обещание доставки. |
| `4 — Поставщик подтвердил` | Получен прямой ответ о ключевых условиях. | Факт покупки и приемки. |
| `5 — Фактическая закупка` | Пользователь реально купил товар. | Только то, чего не было зафиксировано при закупке. |

## 3. Цена, наличие и получение

| Поле | Тип | Правило заполнения |
|---|---|---|
| `Цена предложения` | Number | Видимая или сообщенная цена за одну `Единица цены`. Пусто лучше нуля. |
| `Единица цены` | Select | Пополняемый справочник: `шт.`, `мешок`, `кг`, `м`, `комплект`, `упаковка` и т. д. |
| `Цена и НДС` | Select | Трехсостояние НДС; основное поле для новой работы. |
| `НДС подтверждён` | Checkbox, legacy | Старое бинарное поле. Не отличает «без НДС» от «неизвестно». |
| `Минимальный заказ` | Number | MOQ для указанной цены. Не заполнять предположением. |
| `Кратность заказа` | Number | Шаг заказа/коробки. Например, при кратности 12 потребность 13 округляется до 24. |
| `Город поставщика` | Select | Фактический город отгрузки. Если неизвестен — оставить пустым, а не создавать вариант «не раскрыт». |
| `Наличие` | Select | Отдельный статус доступности. |
| `Количество доступно` | Number | Только подтвержденный или явно видимый остаток. Требуемое количество сюда не копируется. |
| `Способ получения` | Select | Планируемая схема доставки или получения. |
| `Точка отгрузки / самовывоза` | Text | Адрес магазина, склада, павильона или пункта выдачи. |
| `Срок / дата доступности` | Text | Когда можно забрать или получить товар. |
| `Доставка подтверждена` | Select | Подтвердил ли поставщик возможность доставки. |
| `Документы подтверждены` | Select | Подтвердил ли поставщик нужные документы. |
| `Прогноз логистики` | Number | Предварительная стоимость логистики именно этого сценария. |

### `Цена и НДС`

- `Неизвестно` — источник не позволяет сделать вывод;
- `С НДС` — НДС прямо подтвержден;
- `Без НДС` — поставщик прямо сообщил об отсутствии НДС.

### `Наличие`

- `Не проверено` — ответа или надежного остатка нет;
- `Есть` — требуемый товар и необходимое количество подтверждены;
- `Частично` — есть меньше требуемого количества или не вся комплектация;
- `Нет` — поставщик явно подтвердил отсутствие.

`Не проверено` никогда не превращается в `Нет`, а требуемые 5 мешков не превращаются в подтвержденный остаток 5 мешков.

### `Способ получения`

- `Неизвестно` — схема еще не установлена;
- `Самовывоз` — пользователь или водитель забирает товар;
- `Городская доставка` — доставка внутри города;
- `Marketplace` — логистика площадки;
- `Межгород` — отдельная перевозка между городами;
- `Личная поездка` — пользователь едет за товаром самостоятельно.

### Подтверждение доставки и документов

Для обоих полей действуют значения:

- `Не проверено` — сведений нет;
- `Да` — поставщик явно подтвердил возможность;
- `Нет` — поставщик явно сообщил об отсутствии возможности.

Подтвержденная доставка не означает автоматически подтвержденную стоимость: тариф отдельно фиксируется в `Прогноз логистики`, а после выполнения — в фактической логистике.

## 4. Технический и операционный статус

| Поле | Тип | На какой вопрос отвечает |
|---|---|---|
| `Соответствие ТЗ` | Select | Подходит ли сам товар? |
| `Приоритет` | Select | В каком порядке работать с вариантами? |
| `Статус работы` | Select | На каком этапе находится коммуникация и закупка? |
| `Коммерческая готовность` | Select, legacy | Старое смешанное состояние. Для новой работы не использовать. |

### `Соответствие ТЗ`

- `✅ Точное соответствие` — все обязательные технические параметры доказаны;
- `⚠️ Вероятно — подтвердить` — товар выглядит подходящим, но не хватает обязательного параметра;
- `❌ Не соответствует` — доказано отличие по обязательному параметру;
- `⛔ Не найдено` — поиск исчерпан, точного решения нет. Это результат поиска, а не готовый товар.

Техническое соответствие не подтверждает наличие, документы, доставку или выгоду.

### `Приоритет`

- `1 — основной` — проверять первым;
- `2 — резерв` — хороший запасной вариант;
- `3 — уточнить` — слишком много неизвестного;
- `4 — невыгодно` — технически возможно, но экономика плохая;
- `5 — отклонено` — вариант исключен.

Приоритет — ручное операционное решение. Он не равен автоматическому полю `Экономика` и не равен пользовательскому выбору победителя.

### `Статус работы`

| Значение | Смысл | Следующее действие |
|---|---|---|
| `Новый лид` | Вариант только найден. | Проверить карточку и источник. |
| `Нужно связаться` | Вопросы подготовлены. | Пользователю написать или позвонить. |
| `Ждем ответ` | Контакт уже выполнен пользователем. | Дождаться ответа и зафиксировать его. |
| `Подтверждено` | Ключевые условия подтверждены. | Сравнить полную экономику. |
| `Выбрано` | Пользователь решил покупать этот вариант. | Организовать закупку вручную. |
| `Куплено` | Закупка фактически совершена. | Записать цену, количество и доставку. |
| `Недоступно` | Товар получить нельзя. | Перейти к резерву. |
| `Отклонено` | Вариант сознательно исключен. | Сохранить причину в доказательствах. |
| `Устарело` | Сведения потеряли актуальность. | Перепроверить или создать новое наблюдение. |

### `Коммерческая готовность` — legacy

Старые значения: `Нужно связаться`, `Ждем ответ`, `Готово к решению`, `Невыгодно`, `Недоступно`, `Устарело`, `Куплено`.

Поле одновременно смешивает коммуникацию, экономику, доступность и факт закупки. Его заменяют `Статус работы` и `Безопасная экономика`.

## 5. Безопасная прогнозная экономика

Эти поля рассчитывает агент/скрипт после проверки остатка, единиц, фасовки, MOQ и кратности. Старые formula-поля без этих факторов переименованы в `legacy` и не являются основанием для закупки.

| Поле | Тип | Логика |
|---|---|---|
| `Количество к закупке` | Number | Остаток, а не исходное количество тендера. Пусто, если остаток частичной поставки неизвестен. |
| `Минимальный заказ` | Number | MOQ из карточки/ответа поставщика. |
| `Кратность заказа` | Number | Допустимый шаг заказа. |
| `Расчётное количество покупки` | Number | Остаток, поднятый до MOQ и следующей кратности. |
| `Безопасная себестоимость прогноз` | Number | Цена × расчётное количество покупки + логистика. |
| `Безопасная прибыль прогноз` | Number | Тендерная выручка по остатку − безопасная себестоимость. |
| `Безопасная прибыль, %` | Number | Безопасная прибыль ÷ тендерная выручка по остатку × 100%. |
| `Безопасная экономика` | Select | Консервативная классификация результата. |

### `Безопасная экономика`

- `Не рассчитано` — не хватает цены, количества или тендерной суммы;
- `Предварительно — подтвердить` — арифметика положительная, но ТЗ/наличие/доставка/документы ещё не подтверждены;
- `Невыгодно` — прогнозная прибыль отрицательная;
- `Погранично` — прибыль положительная, но ее доля в выручке мала;
- `Выгодно` — положительная доля прибыли выше безопасного порога и коммерческие условия подтверждены;
- `Заблокировано` — доказано несоответствие ТЗ или отсутствие товара.

Публичная карточка с положительной арифметикой получает `Предварительно — подтвердить`, а не зелёный статус.

### Контрольный пример

```text
Корзина, 3 шт.
Тендерная выручка: 850 × 3 = 2 550 ₸
Стоимость товара: 800 × 3 = 2 400 ₸
Прогноз логистики: 1 000 ₸
Полная себестоимость: 3 400 ₸
Прибыль: −850 ₸
Прибыль от выручки: −33,33%
Экономика: Невыгодно
```

## 6. Фактическая закупка

Ручные факты заполняются только после сообщения пользователя или другого надежного подтверждения.

| Поле | Тип | Логика |
|---|---|---|
| `Фактическая цена` | Number | Реальная закупочная цена за единицу. |
| `Фактическое количество` | Number | Реально приобретенное количество. |
| `Дата закупки` | Date | Дата совершенной закупки. |
| `Доля фактической логистики` | Number | Часть реального рейса, распределенная на это предложение. |
| `Стоимость товара факт авто` | Formula | Фактическая цена × фактическое количество. |
| `Итого факт авто` | Formula | Фактический товар + распределенная логистика. |
| `Прибыль факт авто` | Formula | Фактическая выручка − фактическая себестоимость. |
| `Прибыль факт, % от выручки` | Formula | Фактическая прибыль ÷ выручка × 100%. |

Если один рейс стоимостью 5 000 ₸ привез позиции №8, №12 и №15, сумма всех `Доля фактической логистики` должна точно равняться 5 000 ₸. Локальное ядро распределяет остаток до тиына детерминированно.

## 7. Ручные итоги — legacy

| Поле | Замена |
|---|---|
| `Итого прогноз ручной legacy` | `Безопасная себестоимость прогноз` |
| Все formula-поля с пометкой `legacy (без MOQ/остатка)` | Соответствующие поля `Безопасная ...` и `Расчётное количество покупки` |
| `Итого факт` | `Итого факт авто` |

Поля оставлены для сверки старых записей. Для новых предложений их не заполнять.

## 8. Какие поля показывать в рабочих views

### `Поиск / проверка`

Показывает товар, модель, фасовку, источник, соответствие ТЗ, уровень доказательств, наличие, дату и доказательства.

### `Связаться`

Показывает заявку, поставщика, цену, наличие, доставку, документы, вопросы и готовое сообщение.

### `Экономика`

Показывает остаток к закупке, расчётное количество покупки, MOQ/кратность, цену предложения, логистику, безопасную себестоимость, прибыль, процент и безопасную экономику. Legacy-формулы скрыты.

### `Статусы`

Kanban по `Статус работы`: от нового лида до покупки или отклонения.

### `Закуплено / история`

Показывает только фактическую цену, количество, логистику, себестоимость, прибыль, маржу и дату закупки.

## 9. Что является источником истины

| Данные | Источник истины |
|---|---|
| Техспек, требуемое количество, тендерная цена | `Заявки` |
| Постоянные реквизиты и контакты компании | `Поставщики` |
| Цена конкретного товара и условия в конкретную дату | `Предложения` |
| Выбранный коммерческий вариант | `Заявки.Выбранное предложение`, только после решения пользователя |
| Реальная цена и закупленное количество | Фактические поля выбранного `Предложения` |
| Реальная доставка | Пользовательский факт рейса и распределенные доли |

### Как данные попадают обратно в `Заявки`

1. Исходные `Наименование`, `Тех. спек`, `Количество`, `Единица измерения`, город и тендерная цена создаются из файла/OCR/слов пользователя. Предложения их не меняют.
2. Каждое найденное предложение появляется в relation `Заявки.Предложения`; `Количество предложений` считает их автоматически.
3. `Цена каталога, ₸ с НДС` пока обновляется агентом как контролируемый итог самого дешевого технически допустимого варианта. Она не выбирает поставщика автоматически.
4. Пользователь явно выбирает ровно одну запись в `Выбранное предложение`.
5. После этого Notion без пересказа копирует rollup-полями выбранного поставщика, источник, прямое фото, соответствие ТЗ, наличие, статус, цену, логистику, себестоимость, прибыль и прибыль в процентах от тендерной выручки.
6. Пока выбор не сделан, все поля `Выбранный ...` остаются пустыми.

Точность rollup равна точности выбранного `Предложения`: Notion переносит значение точно, но не может проверить, правду ли написал сайт или поставщик. Поэтому уровень доказательств, дата проверки и независимые статусы остаются обязательными.

## 10. Поля, которые после пилота можно удалить отдельной миграцией

Не удалять автоматически. Кандидаты на удаление после пользовательской проверки:

1. `НДС подтверждён`;
2. `Коммерческая готовность`;
3. `Итого прогноз`;
4. `Итого факт`.

До удаления они должны быть скрыты из рабочих views, а старые значения — сверены с новыми полями.

## 11. Текущий пробел экономики

В Notion отдельно учитывается логистика, но пока нет отдельных полей для:

- упаковки;
- погрузки и разгрузки;
- комиссии площадки;
- посредника;
- прочих обязательных расходов.

Локальное детерминированное ядро уже поддерживает `extra_cost`, но добавление соответствующих полей в Notion должно пройти отдельной согласованной миграцией.
