1. Telegram attachment handling (`attachments.py`, `telegram.py`, `queue.py:persist_telegram_message`) validates PDF/DOCX metadata and commits the message, attachment, download job, and acknowledgement outbox together. Duplicate Telegram updates are deduplicated.

That transaction writes a parse version, request item/requirement/financial projections, workflow event, Telegram response, and `prepare_research` job. The deterministic seven-column table parser avoids an LLM for the synthetic tender fixtures and now stores no KZT financial row for unknown currency.
4. `JobWorker._prepare_research` persists the immutable plan and exact `start_research` approval request. The normal callback/approval helper records the owner decision; `start_approved_research` validates the approval and plan hash, consumes it, and atomically creates the run/runtime/job.
5. `ResearchRunExecutor` owns browser calls through `BrowserResearchPort`, validates provider output, then persists source evidence, supplier/contact/location, offers, and offer observations. A deterministic browser fake can exercise the real validation and persistence path; a test-only research implementation must not manufacture directly persisted offers.
6. Native outreach preparation creates conversation targets, drafts and normal WhatsApp approval/outbox work. The existing send worker remains behind account identity, approval, contact, policy and outbound gates. Integration tests must stop at a fake WAHA boundary; they must never use live provider credentials.
7. ## Account pin authorization entrypoint findings

The current pin helper is not fully atomic with ownership authorization: it checks actor/case ownership before the provider call and again before opening the transaction, then locks the account and writes the pin. Ownership or actor activity can change in the gap between the second check and commit. Any authenticated operator API must recheck inside the write transaction after acquiring the account lock, and lock the active actor plus all affected active case owner rows in a consistent order before writing/auditing. Verify lock order against reservation and case-owner update paths. A real PostgreSQL concurrency test must prove deactivation/ownership change cannot race an authorized pin. Do not claim the existing helper fully closes this race until that proof exists.

Same-JID retry currently increments pin_version on every helper call. Keep that conservative invalidation behavior unless a reviewed contract changes it. The future API should distinguish transport retry of the same operator command (stable request idempotency key returns the original result/version) from a new intentional reaffirm/repin command (audited as a new operation, with the version behavior explicit). Do not silently treat repeated same-JID calls as a no-op, and do not let pinning change account hold or circuit state.
