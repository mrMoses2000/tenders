# Owner autonomy review follow-up strategy

## Current entry point and persisted flow

Telegram document intake enters worker._process_intake and cases.persist_intake_result, which binds a default-off owner profile and immutable case/parse snapshot. worker._prepare_research builds and persists the native plan, then owner_autonomy.autostart_snapshotted_research binds the snapshot to a run, consumes the normal approval helpers, starts the existing workflow and enqueues its native execute job. guard_profile_research_work checks revocation at pipeline, parallel task and execute job boundaries. The Mini App exposes owner-scoped read-only provenance and consent profile endpoints.

Owner sourcing evidence currently enters record_sourcing_disposition; the repository accepts only a source_artifacts row joined to a Telegram attachment/message, verifies case and owner, then records an immutable evidence-only disposition. It does not alter accounting or research quantities. This cannot represent an image supplied outside Telegram.

## Intended behavior

Allow one immutable intake snapshot to authorize multiple exact native runs/plans, each independently bound to its run and plan hash. Add a distinct operator-attestation evidence source for a source reference plus verified SHA-256, bound to the authenticated case owner and exact case/item, with the owner assertion and reviewed rationale retained immutably. Retain the existing Telegram artifact route. Both evidence routes stay outside accounting; exact item disposition remains an explicit owner/reviewer action and ambiguous/candidate mappings are never inferred. The workflow continues to use existing research/approval/executor boundaries and respects revocation at native job boundaries.

## Current-case adoption follow-up strategy (before runtime edits)

Add an owner-authenticated preflight for one existing case, then a separate explicit adoption POST. Preflight must read only the exact requested case, active applied parse version, canonical payload hash, current request-item UUIDs/line numbers, owner/project identity, readiness/status, and current consent profile episode/hash. It must not repair/rewrite the case or create projections. Adoption takes the preflight hash plus an explicit owner assertion/reference, locks case/parse/profile, rechecks the exact same values and owner scope, and only then inserts an immutable policy snapshot tied to the already applied parse version and original item IDs. Any drift fails closed. The policy uses the ordered cities `Тараз`, `Шымкент`, `Алматы`; source geography and canonical request stay untouched. Search-city enum adaptation, if required by downstream catalog adapters, is bounded and ephemeral and cannot alter canonical request or source hash. Native plan/approval/start helpers must consume the adopted snapshot, preserve original request_item_id/item_index mapping, and never fabricate Telegram provenance. Testing uses synthetic cases only; no current production case adoption.

Source dispositions need an explicit effective marker distinct from evidence-only records. The existing evidence endpoint defaults to `applies_to_sourcing=false`; projection labels it `evidence_only`, `actual_skip=false`, and `applied_to_plan=false`. An explicit authenticated owner instruction may opt into `applies_to_sourcing=true` for an exact stable request_item_id, exact current canonical parse hash/item identity, bounded unit/quantity, and source reference/SHA. For `operator_attestation`, SHA is explicitly marked owner-declared, not machine-verified; the owner assertion is the sourcing authorization, not an accounting receipt. That instruction can omit a fully sourced item or reduce planned quantity by the explicitly stated already-bought quantity, with planned quantity clamped at zero and a clear-item-only rule. Every generated plan remains bound to the current parse hash, exact item IDs, disposition IDs, and a new immutable plan hash; ambiguous/candidate mappings remain untouched. The current photo has not been imported, hashed, or mapped in this slice; records 3–6 / JSON 2–5 may be entered only by explicit owner review, while candidate rows remain unchanged. No purchase_items/request_items quantities or status are mutated.

Affected files: owner_autonomy.py for exact preflight/adoption and plan filtering; mini_app.py and app.js for owner-visible preflight/explicit adoption and exact source-bound item disposition; migration 044 for append-only adoption/instruction fields needed to pin owner action to parse hash and expose owner-declared SHA (never mutate the applied parse/projection); native integration tests for drift, ownership, stable IDs, evidence-only vs actual skip, and fail-closed plan start. The current case is not exercised or adopted during verification.
