# WhatsApp account operator strategy

Branch `codex/uranenergo-account-operator-2026-10-19`, based on integration checkpoint `2554c7c8682aab06a0672decf747e932675fc11d`. This is isolated implementation only; no live provider, database, service, credential, or outbound action is authorized.

## Current flow and intended behavior

`pin_whatsapp_account_identity` in `whatsapp_account.py` checks session ownership, calls WAHA `GET /me`, then checks ownership again before it starts a transaction and locks `whatsapp_account_controls`. The last authorization can race with actor deactivation or case-owner change. Pinning also increments `pin_version` for every invocation and has no command idempotency. Its existing behavior of not clearing `operator_held` or `circuit_open` is correct and must remain.

Migration 043 leaves historical reservations with the complete account-identity tuple NULL; it does not backfill them. Existing account availability treats every `reserved`/`unknown` reservation as blocking, while daily/contact budget queries include `reserved`, `accepted`, and `unknown`. Legacy unknown outbox replay already avoids account identity/history GET when the stored account identity is NULL. Preserve those original rows and replay behavior.

The smallest changes are:

- `whatsapp_account.py`: after acquiring the account row lock inside the pin transaction, lock the active actor row and all active case owner rows in deterministic UUID order, recheck actor activity and ownership of every active case on the session, then write pin and immutable audit event. Keep an early read-only ownership check before provider GET. Add optional operator command idempotency for new callers; calls without a key preserve existing behavior. A matching retry returns the first version without incrementing it; reusing a key with different actor, expected JID, or reason fails. A fresh key is a new intentional pin version. Neither operation releases a hold/circuit.
- Migration 045: add the idempotency key to the immutable account-control event record and create only the immutable legacy-unknown attestation plus exact reservation-item mapping needed for quarantine. Bind each attestation to a canonical inventory hash, source reference, reason, actor, cutoff, and exact IDs. Use migration 043's `schema_migrations.applied_at` as the legacy cutoff. Add immutable triggers and prevent an event/reservation from appearing in two attestations. Do not update/delete original outbox, reservation, acceptance journal, or workflow state. Do not add a pilot-grant table.
- A narrow `whatsapp_operator.py` handler module accepts the authenticated actor from the trusted application auth context, never from a request body. The current Mini App/API has no operator route in this scope; do not edit `mini_app.py`, `app.js`, worker, or research-owner files. The handler must require exact session/owner scope, key, expected live JID for pin, and source/reason for quarantine. Quarantine is DB-only and makes no provider call.
- Only attested unknown rows whose four migration-043 identity fields are NULL and whose reservation predates migration 043 are excluded from the unresolved-blocking predicate. Bound, partial, or unattested unknowns remain blocking. Leave daily/contact budget SQL unchanged so every unknown remains exposed. Readback adds total unknown, quarantined count, and oldest quarantine age, but never returns full JID, phone, bodies, or provider payloads. Existing explicit hold/circuit gates and fresh-provider-clear requirements remain independent.

## Lock and idempotency contract

Every pin/quarantine transaction uses one lock order: account control row, active actor user row, then affected procurement-case rows sorted by UUID; reservation rows follow only for quarantine inventory validation. Pin performs the final active/all-affected-case check after the account lock and before any pin/audit write. Case owner change and user deactivation tests must race against the final transaction on real PostgreSQL and prove either the action commits before the change with serialized locks or the changed actor/ownership is rejected with no pin/audit mutation. The key is unique per session/action; identical retry returns the stored version/attestation result, while a content mismatch is rejected.

Quarantine input is an explicit sorted UUID set plus a reviewed expected SHA-256. Inside the locked transaction, recompute canonical inventory from database rows including reservation/outbox ID, session, state, conversation/case IDs, reservation time, identity tuple, and source metadata. Require exact ID-set equality, all rows still eligible, all affected cases owned by the active actor, and hash equality before inserting immutable attestation and child mappings atomically. The source reference and reason are mandatory. A stale or partial inventory commits nothing.
