# План: контакты 2ГИС, проверка предложений и рассылка

Состояние проверено 24.09.2026 для пилотной заявки
`10d857bd-81e9-4001-a7b7-cb8b789b66a0` (четыре позиции НИШ Караганда,
поиск в Алматы-1). Это план изменений, а не утверждение, что все поставщики
проверены или получили сообщения.

предложений по «Пакле»; у остальных позиций — ноль. Количество карточек пока
нельзя считать количеством пригодных предложений.

## Текущий поток и разрывы

`Mini App/Telegram → approval → jobs → AGY browser → (только при captcha,
access_denied, login_wall) Codex Chrome → source_evidence/suppliers/offers →
WAHA check-exists → approval → WhatsApp outbox → WAHA → webhook`.

1. Codex fallback умеет `search_suppliers`, но не обогащает контакты уже
   сохранённой карточки по firm ID. Поэтому ранее найденные лиды остаются без
   телефона, даже если он показан в 2ГИС.
2. Категорию магазина агент выбирает из текста техспека в промпте. Стратегия
   поиска, причины выбора категории и исключения не сохраняются отдельно.
   «Алматы-1» сейчас фактически допускает поиск по всему Алматы; географическая
   принадлежность лида не доказывается.
3. Сохранение контакта ссылается на основное доказательство кандидата, а новое
   наблюдение перезаписывает `supplier_contacts.source_evidence_id`. История
   отдельных номеров/ссылок и дата их проверки не представлены явно.
4. Поиск по категории создаёт нерелевантные лиды. Соответствие конкретному
   техспеку, наличие, MOQ и цена остаются неподтверждёнными до ответа или
   другого предметного доказательства.
5. `prepare_supplier_outreach` ограничен одним диалогом на поставщика в заявке
   и пакетом до 20 предложений. Нет кампании «30 подтверждённых адресатов на
   каждую позицию» с прогрессом по позициям.
6. Лимит `daily_limit=10` в проверке отправки вычисляется по сообщениям одного
   диалога, а `minimum_interval` — по его последней отправке. Глобального
   ограничения для одного аккаунта WAHA сейчас нет. Массовая отправка может
   обойти предполагаемую скорость при разных поставщиках.
7. Тихие часы проверяются до постановки WhatsApp в outbox. Одобренное вечером
   сообщение нельзя штатно поставить на утро. Для единственного теста владельца
   временно установлен постоянный user-systemd таймер на 25.09.2026 09:01;
   этот механизм следует заменить общей планировкой в БД.
8. Mini App уже умеет скрывать техспек, этапы и финансовые поля. Нет отдельного
   состояния обогащения контакта, причины отсева лида, стадии доставки
   WhatsApp и настройки отдельных атрибутов предложения.
9. `outbox_events.status='sent'` означает успешную передачу в WAHA. Для
   фактической доставки адресату нужен отдельный статус из webhook/receipt.
   Сессия WAHA ранее требовала ручного перезапуска после `FAILED`.
10. Fallback запускается при CAPTCHA у AGY, но его текущая инструкция запрещает
    терминальному Codex решать CAPTCHA без подтверждения в момент действия.
    Поэтому этот путь может обнаружить блокировку и остановиться; для решения
    CAPTCHA нужен интерактивный режим с участием оператора.

## Целевая схема и порядок работ

### 1. Обогащение сохранённых карточек — приоритет P0

- Добавить задачу `enrich_2gis_firm_contacts` с ключом `(firm_id, дата/версия
  карточки)`; выбирать сохранённые 2ГИС фирмы без свежего контакта.
- Открывать конкретную карточку в серверном браузере, распознавать кнопки в
  единственном и множественном числе, раскрывать контакты и читать только
  блок контактов этой фирмы. Не брать телефоны из «Похожих организаций» и
  рекламы. Сохранять каждый `tel:` и каждый явный `wa.me` отдельно.
- Нормализовать номер, связывать филиалы с одним поставщиком по доказанной
  идентичности, не смешивать чужие номера. Номер без WhatsApp оставлять
  телефонным лидом. Проверять регистрацию в WAHA перед перепиской.
- Сохранять неизменяемое наблюдение контакта: firm ID, исходный URL, исходный
  номер/ссылку, нормализованный номер, тип, время, способ раскрытия,
  `source_evidence_id`. Миграция добавочная; старые контакты остаются валидны.
- Выполнять небольшими порциями с чекпойнтом по карточке, повторами и
  статусами `pending/running/partial/blocked/succeeded`. Не терять успешно
  обработанные карточки при сбое одной или таймауте агента.

**Приёмка:** повторный прогон идемпотентен; десять проверенных карточек дают
контакты на сервере с индивидуальным доказательством; рекламные телефоны не
попадают в поставщика; число лидов без контакта уменьшается.

### 2. Точность поиска и соответствие позиции — P0/P1

- Хранить для каждой позиции структурный поисковый план: тип товара,
  синонимы, категории магазинов, обязательные характеристики, исключения,
  город и геозону, причину выбора. AGY остаётся первым браузерным агентом;
  Codex Chrome запускается только при согласованных ошибках доступа 2ГИС.
- Разделить `найден магазин`, `предположительно продаёт`, `товар подтверждён`,
  `совпадает техспек`. Категория магазина сама по себе не повышает предложение
  до подтверждённого.
- Для «Алматы-1» разрешить выбранный пользователем радиус/район и отмечать
  лиды вне границы. Зафиксировать категорию и запросы в журнале каждой ветки.
- Нерелевантные карточки отсеивать с причиной, сохраняя доказательство для
  аудита. Цена и наличие из 2ГИС не подменяют ответ поставщика.

**Приёмка:** типография и магазин светотехники не входят в список контактов
по плитке без явного доказательства продажи плитки; причины отбора видны.

### 3. Кампания WhatsApp по позициям — P1

- Добавить `outreach_campaign` и `outreach_targets` с ключами по
  `(case_id, request_item_id, supplier_id, channel)`, состоянием подготовки,
  одобрения, очереди, отправки, доставки, ответа и отказа. Для одного
  поставщика с несколькими позициями объединять вопросы в один диалог, но
  сохранять отдельные `conversation_targets` для анализа каждой позиции.
- Считать отдельно найденные карточки, проверенные номера, одобренные
  адресаты, принятые WAHA сообщения, доставленные сообщения и ответы.
  Цель «30 на позицию» относится к проверенным уникальным адресатам, если
  столько реально найдено, а не к числу карточек.
- Ввести атомарный лимит на WAHA-аккаунт и глобальный интервал между
  отправками, плюс существующие пределы диалога и opt-out. Тихие часы
  превращать в `available_at=следующее разрешённое время`; при доставке
  проверять политику снова и переносить событие, если окно закрыто.
- Каждое исходящее сообщение остаётся exact-payload approval и идёт через
  outbox. Входящий ответ привязывать к поставщику и каждой затронутой
  позиции; извлекать наличие, соответствие, количество, цену, НДС, доставку
  и дату с указанием источника, не выдавая догадку за подтверждение.

**Приёмка:** одиночный тест владельца проходит approval → outbox → WAHA →
receipt; повторная диспетчеризация не шлёт второй раз. Кампания соблюдает
общий лимит при параллельных диалогах и показывает прогресс каждой позиции.

### 4. Надёжность и интерфейс — P1/P2

- Мониторить состояние WAHA и браузерного профиля, пробовать ограниченный
  рестарт сессии; при QR/login wall показывать оператору конкретное действие.
  Разделять `accepted_by_waha`, `delivered`, `read`, `failed`, `replied`.
- Для CAPTCHA возвращать задачу оператору с открытой карточкой и возможностью
  продолжить с чекпойнта после действия в интерактивном Chrome.
- Для Mini App добавить панель позиции: воронка поиска/контактов/ответов,
  таблица предложений с фильтрами по соответствию, цене, наличию и району,
  доказательство рядом с полем. Сохранять пользовательские настройки
  видимости отдельных колонок и компактный мобильный пресет.
- Стабилизировать публичный HTTPS адрес Mini App именованным туннелем и
  мониторить внешний health, а не только локальный порт.

**Приёмка:** пользователь видит конкретный товар, подтверждённый объём
поставки/приёмки, статус контакта и причину отсева; техспек и второстепенные
атрибуты скрываются одним действием. Ссылка Mini App переживает рестарт.

## Риски совместимости

Нужны добавочные миграции для истории контактов, поисковой стратегии,
кампаний и статусов доставки; старые `offers`, `supplier_contacts`,
`action_approvals` и outbox продолжают читаться. Миграции выполнять после
снимка БД и сухой сверки дублей по `firm_id`/телефону. Старые данные Notion
и импортированные статусы не переписывать. Серверный прогон Chrome и отправка
по 30 на позицию требуют отдельной живой проверки после реализации.
