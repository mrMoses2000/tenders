# Задание удалённому агенту: следующий production-срез procurement bot

## Как подключиться

Команду SSH предоставляет владелец отдельно. Не сохраняй её, пароль, токены или содержимое
`.env` в Git, логах, отчётах и сообщениях. После подключения:

```bash
cd /home/moses/tenders
git status --short
git pull --ff-only
.venv/bin/procurement-bot health
.venv/bin/pytest -q
.venv/bin/ruff check src tests
```

Рабочая ветка — `main`. Не удаляй и не переписывай пользовательские данные. Не используй
`git reset --hard`, `git checkout --`, destructive SQL или повторную авторизацию WhatsApp.

## Контекст системы

Владелец общается с ботом в Telegram. Бот принимает текст, PDF/DOCX и голосовые, создаёт
структурированную заявку в PostgreSQL, уточняет недостающее, ищет поставщиков и после явного
approval общается с ними через WhatsApp/WAHA. Секреты находятся в `.env`, внешний ключ
AssemblyAI читается из `/home/moses/audio_transcription/.env`; значения нельзя выводить.

Уже внедрён детерминированный слой `dialogue_routing.py` и миграция
`012_dialogue_turns.sql`. Intake разрешён только для маршрутов `create_request` и
`update_request`. Вопросы статуса, закрытие позиции и обычные реплики обрабатываются отдельно.
AGY только извлекает факты в строгую схему и не выбирает действие с БД.

## Основная задача

Довести память диалога и управление несколькими заявками до production-уровня, не ослабляя
детерминированные границы.

1. Добавь единый durable ledger исходящих Telegram-сообщений.
   - Новая immutable migration `013_...sql`; миграцию `012` не изменять.
   - После успешной Telegram-доставки текст/документ должен быть связан с точным
     `outbox_event_id`, `external_message_id`, chat и владельцем.
   - Завершение outbox и запись сообщения должны происходить одной DB-транзакцией.
   - Retry обязан быть идемпотентным; callback answers не являются сообщениями чата.

2. Реализуй типизированный `DialogueContextRepository`.
   - Источники истины: текущая applied-версия заявки, единственный открытый вопрос,
     сохранённые `dialogue_turns` и транспортный ledger.
   - В extractor передавать только текущую нормализованную заявку и один открытый вопрос.
     Не передавать весь сырой чат и не позволять истории менять маршрут/side effect.
   - Добавь read-only диагностический метод/CLI, который показывает контекст без секретов,
     UUID пользователю и сырого содержимого документов.

3. Добавь безопасное управление новой заявкой при уже открытой.
   - `Создай новую заявку` не должно молча перезаписывать текущую.
   - Бот должен показать человеческое название активной заявки и попросить отдельное
     подтверждение отмены/переключения.
   - Только точное подтверждение атомарно отменяет старый draft и создаёт новый.
   - Повтор сообщения/retry не создаёт второй case.

4. Добавь RU/KK локализацию диалога.
   - Язык текущего транскрипта/сообщения → сохранённое предпочтение → Telegram language code.
   - Все системные ответы проходят через типизированный каталог сообщений.
   - UUID, hash, enum, название worker/provider и технические причины наружу не выводятся.

## Обязательные проверки

- Unit-тесты маршрутов: приветствие, off-topic, `Что там?`, явный поиск, список с количеством,
  ответ на уточнение, новая заявка при активной, повтор/retry.
- PostgreSQL integration: atomic outbound ledger, ровно один applied dialogue turn и case на
  одно message ID, rollback при drift.
- Полный `pytest` и Ruff должны пройти.
- Применить новые миграции через `.venv/bin/procurement-bot migrate`.
- Перезапустить `procurement-agent-bot.service`, проверить health и журнал запуска.
- Для live Telegram smoke-test не имитировать пользователя и не отправлять сообщения от его
  имени. Попросить владельца прислать: `Привет`, `Что там?`, затем тестовую заявку; проверить
  БД/логи после каждого хода.

## Жёсткие границы

- Не отправлять сообщения поставщикам и не запускать внешний поиск без существующего approval.
- Не давать AGY/MCP доступ к SQL, `.env`, основному HOME или лишним инструментам.
- Не создавать таблицы по свободному тексту пользователя: только versioned migrations.
- Не удалять историю заявок/сообщений; исправления оформлять новыми событиями/версиями.
- Не менять уже применённые migration-файлы.

После выполнения оставь краткий отчёт: изменённые контракты, миграции, тесты, команды запуска,
остаточные риски и commit hash. Закоммить и отправь изменения в `main`, если владелец не дал
другую ветку.
